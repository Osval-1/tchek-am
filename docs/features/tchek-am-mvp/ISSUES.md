## Conventions (apply to every issue)
- **Layout:** Django project package `tchekam` in `src/tchekam/`. Apps are `tchekam.<app>`. Settings are `tchekam.settings.{base,dev,test,prod}`, read from environment variables via `django-environ`. Tests go in `tests/<app>/` and use `pytest` + `pytest-django`.
- **Tooling:** `uv` for dependencies, `ruff` for lint and format, Python 3.13. Run `uv run pytest` and `uv run ruff check .` before finishing.
- **Database:** PostgreSQL 16 + pgvector (`docker compose up -d db`). Tests run against Postgres, not SQLite.
- **External services** (WaSender, Claude, Groq, SerpAPI, R2) always sit behind an adapter interface, with a `Fake*` implementation used in tests. **No test makes network calls.**
- **Background work** goes through `tchekam.core.tasks.enqueue(task_name, **kwargs)` (Issue 2). In test settings, tasks run eagerly and synchronously.
- **Copy:** every user-facing string goes through the i18n catalogue (Issue 5), in fr, en and pcm (Pidgin). Never use "scammer", "fraud", "arnaqueur" or "escroc" in copy.
- **Privacy:** never log message bodies, evidence or phone numbers at INFO level or above. Use `tchekam.core.redact()` in logs.
- **Tiers:** JUNIOR = isolated, well-scoped work. MID = design judgment and cross-module work. SENIOR = architectural, security-sensitive or trust-critical work.

## Issue 3: Messaging adapter and WaSender webhook (echo bot)

**Tier**: SENIOR
**Description**: Create the `tchekam.messaging` app. Read `docs/integrations/wasender.md` first.
- **`MessagingChannel` interface:** `send_text(to, text)`, `send_image(to, image_url, caption=None)`, `send_typing(jid, ms)`, `download_media(inbound_message) -> (bytes, mimetype)`, `leave_group(group_jid)`, `group_metadata(group_jid)`.
- **Normalised `InboundMessage` dataclass:**
  - `message_id`, `sender_phone` (E.164 or digits), `sender_jid`
  - `chat_type` (private | group), `group_jid`
  - `kind` (text | image | audio | contact | other)
  - `text` / `caption`, the raw media descriptor, `timestamp`
- **Implementations:**
  - `WaSenderChannel`, using httpx with the endpoints from the notes and a 10 s timeout. On a `retry_after` response it raises `RateLimited(retry_after)`.
  - `FakeChannel`, which records sent messages for tests.
- **`get_channel()` factory** chosen by setting.
- **Parser** `parse_wasender_payload(dict) -> InboundMessage | None`, defensive about every documented variant:
  - accepts all of the event names;
  - accepts both `data.messages` and `data`;
  - ignores `fromMe`;
  - takes the sender from `cleanedSenderPn` or `cleanedParticipantPn`;
  - recognises groups by `participant`.
- **Webhook view** `POST /webhooks/whatsapp`:
  1. Verify `X-Webhook-Signature` against `WASENDER_WEBHOOK_SECRET` with `hmac.compare_digest`, returning 401 on mismatch.
  2. Store an `InboundEvent` (unique `message_id`, raw payload JSON, received_at, processed_at, status) idempotently; a duplicate gets 200 and is not re-enqueued.
  3. Enqueue `messaging.process_inbound(event_id)` and return 200 with no other work.
  4. CSRF-exempt, and accepts only POST.
- **Temporary handler:** `process_inbound` echoes the text back ("Tchek-Am received: …"). Issue 5 replaces it with the router.
- **Fixtures:** sample payloads for private text, group text, image, audio and `fromMe`, in `tests/messaging/fixtures/`.

**Acceptance Criteria**:
- [ ] A missing or wrong signature gets 401 and nothing is stored.
- [ ] A valid payload gets 200, stores one `InboundEvent` and enqueues once. Sending the same payload again gets 200 with no new row and no enqueue.
- [ ] Parser tests cover every fixture variant, including both event-name styles and both envelope shapes. `fromMe` returns None. Groups are detected.
- [ ] Under `FakeChannel`, the echo reply goes to the sender.
- [ ] No module outside `tchekam.messaging` imports `WaSenderChannel`. An import-linter-style test greps for this.
- [ ] Unit tests (httpx MockTransport) check that `WaSenderChannel` sends the correct JSON and Bearer header, and turns a `retry_after` response into `RateLimited`.

**Files likely affected**: `src/tchekam/messaging/{__init__,apps,channel,wasender,fake,parser,models,views,tasks,urls}.py`, `src/tchekam/urls.py`, `tests/messaging/*`
**Dependencies**: 2

## Issue 5: Conversations: users, sessions, i18n and the input router

## Issue 7: Reputation engine: bands, red threshold, independence, decay

**Tier**: SENIOR
**Description**: Create `tchekam.reputation`, with **pure functions** that implement ADR-005, ADR-006 and ADR-007 exactly.
- **`compute_band(subject, now) -> BandResult`**, where `BandResult` holds `band` (green | yellow | orange | red), `approved_count`, `independent_reporters`, `pending_count`, `last_report_date`, `single_report_with_proof` (bool), `under_appeal` (bool).
- **Rules:**
  1. Rejected and merged reports never count.
  2. Approved reports aged 24 months or more (from `decided_at`, or `incident_date` if earlier) are ignored for public purposes.
  3. 🔴 if (≥ 3 independent approved reporters **or** ≥ 1 approved report with `has_payment_proof`) **and** ≥ 1 approved report aged under 12 months. Only reports aged under 24 months count toward this.
  4. Otherwise 🟠 if there are any approved reports aged under 24 months. This includes the case where every approved report is 12–24 months old.
  5. Otherwise 🟡 if there are any pending or needs_info reports.
  6. Otherwise 🟢.
- **Independence:** `independent_reporters(reports) -> int` builds clusters of reporters. Two reporters are **dependent** if any of these holds:
  - they are the same BotUser;
  - one report's subjects include the other reporter's phone number;
  - their reports were submitted within 10 minutes of each other **and** share an evidence sha256 or have text similarity ≥ 0.9 (use `difflib` on `summary_final`).

  The count is the number of connected components (union-find).
- **Reporter weight:** reporters with `trust_weight < 0.3` are excluded from the independence count (used by Issue 16).
- **Appeals:** an approved appeal with a `number_acquired_at` date excludes all reports with an incident or submission date before it (a hook used by Issue 22; read via a small query function).
- **Caching:** `band_for_phone(e164)` caches results for 1 h, keyed by subject. `invalidate(subject)` is called on any moderation decision. Time-based expiry means decay applies even without new events.

**Acceptance Criteria**:
- [ ] Table-driven tests cover each band, including these cases:
  - [ ] 2 independent reporters gives 🟠; 3 gives 🔴.
  - [ ] 1 report with proof gives 🔴.
  - [ ] 3 reporters, all 13 months old, gives 🟠.
  - [ ] An approved report aged 25 months is ignored.
  - [ ] Pending-only gives 🟡.
  - [ ] Rejected-only gives 🟢.
- [ ] Independence tests cover each dependency rule and transitive clustering (A~B, B~C gives 1 component).
- [ ] A frozen-clock test shows a 🔴 decaying to 🟠 after 12 months with no new report.
- [ ] Each band has a property-style test that no single reporter, however many reports they file, can produce 🔴 without payment proof.
- [ ] 100% branch coverage on `reputation/rules.py`.

**Files likely affected**: `src/tchekam/reputation/{rules,independence,service,cache}.py`, `tests/reputation/*`
**Dependencies**: 6

## Issue 8: Number check (F1), end to end

**Tier**: MID
**Description**: Create `tchekam.checks.number`.
- **Input:** the router passes a normalised number, or several, in which case check up to 3.
- **Steps:**
  1. Get or create the `PhoneNumber` and increment `check_count`.
  2. Compute the band (Issue 7).
  3. Gather masked linked account names from approved, confirmed subjects in reports aged under 24 months.
  4. Count checks this calendar month from `CheckLog`.
  5. Build the reply from catalogue keys.
- **The reply includes:** the formatted number and operator; the band emoji and factual sentence; the date of the last report (orange or red); "1 reviewed report with payment proof" when applicable; "under appeal" when applicable; up to 3 masked names; "checked N times this month"; safety tips; and how to report (menu 4) and how to appeal.
- **Logging:** write a `CheckLog`.
- **Rate limit:** 30 checks per user per day (setting), after which a polite catalogue message is shown.

**Acceptance Criteria**:
- [ ] There's an end-to-end test for each band (webhook payload through to the `FakeChannel` reply text) in at least fr and en.
- [ ] Replies never contain a reporter's number. A test seeds a report whose reporter number is known and asserts it's absent from every reply.
- [ ] Names are masked. Pending report details never appear, only the count.
- [ ] The 31st check in a day gets the rate-limit message, and no `CheckLog` is written for it.
- [ ] Checking with a payment-proof report present shows the single-report wording.

**Files likely affected**: `src/tchekam/checks/{number.py,limits.py}`, `src/tchekam/i18n/catalog.py`, `src/tchekam/conversations/router.py`, `tests/checks/test_number.py`

## Issue 9: AI module: Claude client, prompt registry, evidence extraction, evals

## Issue 11: Report flow, part 1: start, collect evidence, extract

**Tier**: SENIOR
**Description**: Create `tchekam.reports.flow`, a conversation flow handler. Steps:
1. **Start**, from menu 4, a keyword or audio. Create a draft `Report` and explain what to send (screenshots of the chat, the MoMo/OM SMS, the product post; plus a voice note or text describing what happened). The user sends `FINI` / `DONE` / `1` when finished.
2. **Collect.**
   - Each image or audio: `download_media` immediately, `ObjectStore.put`, then an `Evidence` row with its sha256.
   - Audio: transcribe via `speech` in a task.
   - Text messages are appended to `state["story"]`.
   - Limits: 10 evidence items and 15 MB in total.
   - Acknowledge each item briefly ("✅ 2 images, 1 voice note received").
3. **Extract.** On DONE, enqueue `reports.extract(report_id)`, which:
   - runs `ai.extract_evidence` over all images plus the transcripts and story;
   - stores the result on the report (`summary_ai`, `scam_type`) and on each evidence item (`ai_extraction`, `kind`, `tamper_flags`);
   - creates `ReportSubject` rows (source=ai, confirmed=False);
   - hands over to the confirm step (Issue 12).
4. **Unclear audio.** If the transcript confidence is below 0.4, or no number or amount was found anywhere, ask the user to type the seller's number and the amount.
5. **Resume.** Message within 24 h of the last activity and the flow continues. After 24 h, the next message starts fresh and offers to resume.

Set `last_activity_at` on every step.

**Acceptance Criteria**:
- [ ] The flow test (FakeChannel, InMemoryObjectStore, FakeLLMClient, FakeSpeechToText) goes: start → 2 images + 1 audio + text → DONE → extraction persisted → confirm step reached.
- [ ] Media is stored under generated keys. `Evidence.sha256` is set.
- [ ] A low-confidence transcript with no number leads to the "please type the number" prompt.
- [ ] The 11th item is refused politely, and so is anything over the size cap.
- [ ] Resume works at 23 h. At 25 h the user is offered a resume.

**Files likely affected**: `src/tchekam/reports/{flow.py,tasks.py}`, `src/tchekam/i18n/catalog.py`, `src/tchekam/conversations/router.py`, `tests/reports/test_flow_collect.py`
**Dependencies**: 6, 9, 10

## Issue 16: Report linking, reporter weighting (R3) and evidence score

**Tier**: MID
**Description**:
- **`reports.link(report_id)`** creates `ReportLink` rows to other non-rejected reports that share a confirmed or AI phone subject (same_number), an account name (same_name), an evidence or product image with the same sha256 or a pHash distance ≤ 8 (same_image, once Issue 17 lands; until then use sha256 only), or a `summary` difflib ratio ≥ 0.85 (similar_text).
